# Skills 合集设计

## 目标

让每个 skill 都可以被独立发现、审查和安装，同时让合集能够随着新能力加入而保持清晰。仓库关注可复用的工作决策和验收方法，不替代项目仓库、知识库或客户交付目录。

## 信息架构

```text
Skills/
├── README.md                         # 人可读的目录与入口
├── CONTRIBUTING.md                    # 新增、验证与 PR 约定
├── docs/
│   └── collection-design.md           # 合集级设计决策
└── <skill-name>/                      # 一个可独立使用的 skill
    ├── SKILL.md
    ├── agents/                        # 可选的 Codex UI 元数据
    ├── references/                    # 可选的按需说明
    ├── scripts/                       # 可选的可执行辅助工具
    └── assets/                        # 可选的产物资源
```

第一层直接放 skill 文件夹，避免额外嵌套造成安装或按路径引用时的歧义。随着数量增加，使用统一的命名前缀和 README 分类管理，而不是过早按目录树拆分。

## 命名与分类

- 名称使用“领域 + 动作/结果”的连字符形式，例如 `cad-dimension-comparison-table`。
- README 以任务分类展示，例如表格审核、CAD、文档、研发流程；一个 skill 只登记在最贴近其主要用途的分类中。
- description 负责让 Codex 正确选择 skill；它应说明能力和适用边界，避免用宽泛词覆盖无关任务。

## Skill 质量门槛

每个 skill 至少应说明：

1. 需要得到的结果及适用范围。
2. 容易造成错误的约束、映射规则或权限边界。
3. 合理的验证方式，以及不能据此声称已经证明的事情。

把仅在特定模式下需要的长说明放入 `references/`；把经常重复且需要确定性执行的逻辑放入 `scripts/`。不要为凑结构创建空目录、占位样例或重复文档。

## 维护流程

新能力从一个目的明确的分支开始，经过验证后以中文 PR 提交。PR 应说明它解决的可复用问题、主要变更、验证证据、风险与不覆盖的范围。合并由仓库所有者审核决定。

对已有 skill 的修订优先使用真实使用中发现的问题来驱动。修正应尽量小而可追溯，避免把单个项目的偶然情况扩大为所有任务的硬规则。
